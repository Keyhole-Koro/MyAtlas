# データの旅（data-journey）

## アイデア

関数ではなく、データを追う。

UI の要求の流れでは、アプリが OS に出す要求の封筒 **Request**（`schema.request` の 10 個のフィールド）を主役にした。
行がフィールド、列が手順。地図の「中の紙」（`os.gateway` と `os.submit`）は、その場に開いて順に並べた（全 22 手順）。
各マスには、その手順がそのフィールドに何をするか（詰める・写す・上書き・差し替え・何語目・使う…）を印で置き、
行の線の色で「いまその値がどのメモリにあるか」を見せる。

- 橙＝アプリのメモリ、黄＝OS 側。斜線は「OS 側にはあるが、まだアプリの値（owner）・アプリのメモリを指す（s0・s1）」。
- 手順 5 で全部のフィールドが一斉に「写す」になり、線が橙から黄に変わる（境界を越える）。
- 手順 12 までに斜線が全部消える。地図の文「OS 側の値だけになった Request」が、そのまま絵になる。
- **owner の上書き（手順 6）** は赤い印と、行の中の吹き出し「アプリは名乗れない」で強調。詳しい欄には、地図の文・コードの行
  （`gateway.unsafe.mln:212 request.owner = (i32)pid;`）・アプリ側が入れていた値（`runtime.send` の `current_owner`）・
  その owner が後で何に使われるか（ノードの持ち主、REPLY の宛先）をまとめた。
- 表が追うのは 1 つの具体的な要求（`send_text` が出す SET_TEXT）。この要求で起きないことは点線の印にした
  （手順 11 の差し替え、手順 20 の書き戻し）。詰めないフィールドには灰色の「0」（s1 は `""`）。

表の下の **「どこにある？（置き場ごと）」** は、置き場（アプリのメモリ／受け皿／OS 側の Request／words[24]／要求の列／service task）
を横の帯にして、そこに何があるかを手順から手順までの棒で描く。棒は交差しない。置き場の間を動く所だけ、その手順の列に短い矢印がある。
選んだ手順にある棒だけが濃く、ほかは薄くなる。Request が「アプリのメモリ → OS 側の Request → words[24] → 列 → service task」と
階段のように降りていくのが見える。

**パケット**（アニメーション）では同じ手順を劇として再生する。Request のカードがアプリのメモリから OS 側へ 1 行ずつ写り、
owner の行に pid が飛び込み、文字が境界を越えて受け皿に落ち、フィールドが 1 つずつ 24 語のマス目に入り、そのマス目が列（32 枠のリング）の
1 枠に縮んで入る。service task で名前のあるフィールドに戻って DOM の Label を書き換え、結果の 1 語がアプリに戻る。
値は、飛んでいる写しが着いた時に現れる（着く前に答えが見えない）。

**CPU 時間**も同じ形でやった。行は「時計の tick 数・進み → now → spent → 置き場 3 つ → CpuTimes・procs → t.last・%・系列」。
2 つの周期（切り替えのたびに足す／1 秒ごとに読む）を縦の点線で分けた。最後の手順から「UI の要求の 1 へ」で、
% の文字が Request の s0 になる話へつながる。

## 使い方

- 開くと「UI の要求」の表。手順 6（owner = pid）が選ばれている（地図の `start` と同じ所）。
- 「▶ 再生」は、まだ手順を選んでいなければ **手順 1 から** 流す（境界を越える手順 5 も必ず通る）。手順を選んだ後は、そこから流す。
- 列（手順）・行（フィールド）・印・下の帯の棒をクリックすると、上の帯に一言、下に 3 枚の欄（地図の文／フィールドに起きたこと／コード）が出る。
  同じ理由で同じ印を持つフィールドは 1 つにまとめて出す（手順 13 の 11 個の「何語目」など）。
  行の名前をクリックすると、その行の旅（左から順の一覧）とコントラクトの宣言行。
- ← → で手順を動かす。Space で再生と停止。
- 「もし列が満杯なら」で、満杯の時の 3 手順を差し込む。その列はうすい幕がかかり、本筋から外れた分かれ道だと分かる。
- 「パケット」で再生画面。⏮ ◀ ▶ ▶▶、目盛りのクリック、速さの切り替え。下の帯は記録（Editor で「x」を打った 1 回）。
  その手順に当たる記録の行が、命令数の軸に青く出る。まだ手順を選んでいなければ手順 1 から始まる。
- CPU のパケットでは、置き場（3 つ）をクリックすると、持ち主がユーザスレッド／カーネルスレッド／None の場合を切り替えて見られる。
- URL の `#j=ui&v=packet&c=os.gateway:1` で、流れ・見せ方・手順を指せる。
- 表は幅 1,210px くらいから横スクロールなしで収まる（CPU は 1,180px、満杯の分岐を入れると 1,340px）。
  それより狭いと横にスクロールするが、フィールドの名前の列は左に残る。
- 幅 760px 未満（スマホ）では、表は「手順のカードの列」になる。パケットは画面の幅がおよそ 790px より狭いと **絵コンテ** になり、
  その手順が使う置き場だけを、メモリの帯（アプリのメモリ／OS 側…）の中に縦に並べる。写す元と写す先が、いつも同じ画面に入る。

## 何を見せているか（出どころ）

- 印は、手順の `data.fields`・手順の文（label）・`schema.request` のフィールドの文・その手順の箱の点の文から決めた。
  印ごとに出どころ（どの文か）を詳しい欄に引用で出す。読み込み時に、渡すデータのフィールドに印が無い／引用した句が文に無い／
  「ずれ」の欄が引く地図の文が変わった、を確かめる仕組みがある（地図が変わると「確かめて」と出る）。
- 地図が黙っている所だけ、`lab/data/src` のコードから取った（取った行は毎回ファイルから探して行番号ごと表示）：
  0 で埋めた Request と `s1 = ""`（`runtime.ui_request`）、owner に入る `current_owner`、result_out が 0 なら差し替えないこと
  （`gateway.unsafe.mln:139`）・書き戻さないこと（同 `:251`）、SET_TEXT の結果が OK、語の順（`RequestWord`）、
  total ＝ `g_clock_charged − g_clock_base`、share の式、t.cpu の中身。
- 具体的な数は、地図の図 `fig.clock-word` の例（1,234 tick と 128/256 → 316,032）と、記録の命令数だけ。ほかは記号（「文字」「pid」）。
- 記録の帯：2 つ目の REQUEST（Label_text が送ったもの）の各手順を、イベントの seq で対応させた。
  例：手順 6 は記録に出ない（request() の中の 1 行）、手順 19 は 命令 512,630 `ui_protocol.set_text`。

## うまくいったこと

- 「境界を越える」「OS 側の値だけになる」「owner は名乗れない」が、説明を読む前に線の色と印の並びで見える。
- 手順 5 の列が「写す」の壁になり、手順 13 の列が `#0〜#15` の語番号になる。表のまま「形が変わる」のが分かる。
- 地図の文・フィールドの文・コードの行を、印 1 つから辿れる。コードは本物の行（行番号つき）。
- 置き場の帯は、棒が交差せず、矢印は動く手順の列にだけある。選んだ手順の棒だけ濃いので、その時どこに何があるかが一目で分かる。
- パケットは状態を毎回はじめから組み立てるので、目盛りで飛んでも戻っても絵がずれない。1 つ進む時だけ動きを再生し、
  値は写しが着いてから現れる。次の手順に進むと、飛んでいる途中の写しは止めて、隠していた値を出す。
- スマホの絵コンテは、手順ごとに使う置き場だけを出すので、文字が小さくならず、元と先が両方見える。
  アプリのメモリの帯が名前だけに縮んでいても、境界の線は残るので「いま OS 側にいる」が分かる。
- CPU の流れの最後から UI の要求へ渡れる（データの旅が 2 つの流れをまたいでつながる）。
- ダークモード、スマホ幅、画面の回転・ツールバーの伸び縮み、reduced-motion（飛ぶ写しも、CSS の動きも止まる）に対応。
  外部ライブラリなし（素の JS・SVG・CSS）。フォルダは 0.3 MB ほど（スクリーンショットを除く）。
- 全手順を 2 つの流れ・2 つの見せ方・5 つの画面（1440／ダーク／1024／スマホ／reduced-motion）で流す検査で、
  コンソールのエラーと警告は 0。スマホで高さを変えた後・回転した後にカードを押しても、詳しい欄は壊れない。

## うまくいかないこと・限界

- 表とパケットの印は、手順ごとに手で書いた対応表（`js/journeys.js`）から作っている。地図の文から自動で読むのではない。
  確かめる仕組みはあるが、新しい流れには対応表を足す必要がある。置き場の帯の棒と矢印も手で書いた。
- 表は 1 つの要求（SET_TEXT）を追う。ほかの op（結果を受け取る `ask_i32` など）では、点線の印が実線になる。op を切り替える機能は無い。
- パケットには満杯の分岐が無い（表だけ）。
- 記録は Editor の 1 回分で、タスクマネージャの TIMER や PROC_STATS は入っていない（その手順では「記録に無い」と出す）。
- パケットのカードの値は記号。実際の pid やノード番号、文字の中身は記録に無いので出していない。
  グラフの系列の棒は「1 秒に 1 つ」を示す枠だけで、値は描いていない。
- 1,440×900 では、表の下の置き場の帯は画面の下にはみ出す（少しスクロールすると全部見える）。
- 790〜1,360px のパケットは、舞台を 0.86 倍にしてカメラが動きを追う。帯の名前は左端に貼り付けて出すが、
  動く所によっては置き場の一部が画面の外になる。

## 見つかったこと（地図のずれ）

データを語単位で並べたら、地図の数が古いことが見えた。

- 地図：`gateway.read`「13 語を読む」、`channel.encode`／`os.submit` の紙「Request を 0〜12 語目に、返事の channel を 13 語目に」、
  `channel.words` のフィールド `words[0..12]`・`words[13]`。
- 実際：`schema.request` のフィールドは 15 語（a0 … a5 は 6 語）。コードの `RequestWord` は S1_LEN が 14、REPLY_CHANNEL が 15、
  `REQUEST_WORD_COUNT = 15`（`channel.unsafe.mln`）。`read_user_request` のコメントも 15 語。
  s0_len・s1_len を足した時に、地図（と `submit`・`request()` のコメント）が 13 語のまま残ったように見える。
- 表では手順 5 と 13 に「!」を付け、詳しい欄とパケットの吹き出しで両方を見せた。`make atlas-check` は記号の場所しか見ないので、
  こういう数のずれは拾えない。

もう 1 つ、レビューで分かった省略：

- 地図（`gateway.stage` の文、Request の result_out の説明、手順「差し替え」）は、result_out を「差し替え、返事で書き戻す」とだけ書く。
  コードが差し替えるのは `result_out != 0 && result_size > 0` の時だけで、send_text の SET_TEXT は result_out を詰めない（0）ので、
  差し替えも書き戻しも起きない。表では手順 11 に「!」を付け、地図の文 2 つとコードの行 2 つを並べた。

## レビューのあとで変えたこと

- **スマホで画面の大きさが変わると壊れた**（詳しい欄が消え、「null」が出て、押すたびにエラー）：詳しい欄を参照で持ち、
  手順のカードの列を作り直す前に外へ戻すようにした。高さだけの変化（ツールバー）では表を作り直さない。
  390px の全画面撮影（`--full`）もエラーなしで通る。
- **表とパケットで result_out の話が食い違っていた**：表もこの要求（SET_TEXT）に合わせた。手順 2 は灰色の「0」、手順 5 の後は斜線なし、
  手順 11 と 20 は点線の印「この要求ではしない」。地図が条件を書いていないことを「!」で示した。パケットの吹き出しも同じ話にした。
- **再生が手順 6 から始まっていた**：手順を選ぶ前は、表でもパケットでも手順 1 から流す。パケットは開いた時も手順 1。
- **1,280〜1,366px で表がはみ出し、横に動かすとフィールド名が消えた**：名前の列を別の SVG にして左に貼り付けた（sticky）。
  列の最小幅を 46px にし、見出しは切らずに字を小さくする。1,210px 以上なら横スクロールなし。
- **パケットで満杯の分岐を入れていると → で手順 1 に戻った**：パケットに入る時に満杯の分岐を外し、← → はパケット自身の手順だけを歩く。
- **上の帯「どこにある？」が読みにくかった**（9 本の線が交差、11px の灰色の注記、words[24] と列の取り違え）：置き場ごとの棒と短い矢印に描き直した。
  words[24] の帯を足し、Request が列に入るのは手順 15 から。選んだ手順に無いものは薄くする。文字は 12px。表のいちばん下へ移し、フィールドの表を先にした。
- **スマホのパケットで「どのメモリか」が分からなかった**：絵コンテ（その手順の置き場だけを帯の中に縦に並べる）にした。
  790〜1,360px では、帯の名前を左端に貼り付ける。
- 細い列（7・10・16・17 と CPU の 2・3・9）に、縦書きのひとこと（呼ぶ・通知・起こす・戻る）を付けた。
- 同じ「走る所」は表のどこでも同じ名前にした（いちばん狭い所に入る名前を全部で使う）。
- reduced-motion で、飛ぶ写し（Web Animations）も止める。
- 動きの途中で値が二重に見えた：着くまで値を隠し、写しには背景を付けた。words[24] へは行ごとではなく小さな札が飛ぶ。
  リングの 1 枠への飛び先も直した（前は SVG の要素に飛ばしていて、位置が取れていなかった）。head と tail の字が重ならないようにした。
- 薄い灰色の字（`--text-3`）を濃くした（白地で 4.5:1 以上）。
- 印の無い行の線の理由（`c.note`）を詳しい欄に出す。詳しい欄の名前の列を 96px にした。CPU のカードの値を短くした（切れない）。

## 本体の viewer に取り入れられること

1. **データの行×手順の表**：今の「渡すデータ」欄は 1 手順ずつだが、フィールドを行にして全手順を並べると、
   どこで写り、どこで差し替わり、どこで使われるかが一目で分かる。`schema` を持つ流れなら同じ作りで出せる。
2. **線の色＝メモリの場所、斜線＝まだアプリ次第**：境界の安全の話（gateway の役目）を、色 2 つと斜線 1 つで言える。
3. **中の紙をその場に開いて並べる**：紙に入る・出る操作をせず、番号を通しで振る。地図の番号は詳しい欄に残す。
4. **印 1 つ → 地図の文の引用 → コードの行**の 3 段の出どころ表示。とくにコードは行を文字で探して番号を出す（ずれない）。
5. **置き場ごとの棒の帯**：どこに何があるかを、交差しない棒と、動く手順にだけ置く短い矢印で描く。選んだ手順に無いものは薄くする。
   線を引き回すより、ずっと読みやすい。
6. **具体的な 1 回を追う時は、その 1 回で起きないことを点線にする**：地図の一般的な文と、具体的な要求の動きを、矛盾させずに並べられる。
7. **スマホでは絵コンテ**：その手順が使う置き場だけを、メモリの帯の中に縦に並べる。大きな図を縮めて動かすより、字が読める。
8. **記録を命令数の軸で手順に重ねる帯**：その手順が本当に起きた時刻と、走っていたスレッドが見える。
9. 地図の文と、コード・スキーマの数の食い違い（語数・容量など）と、条件の省略（「差し替える」だけ）を見つける検査を atlas-check に足す価値がある。

## ファイル

- `index.html`：入口。`../data/atlas.js`・`../data/code.js` を読む。
- `js/journeys.js`：2 つの旅（列・行・印・置き場の帯）を ATLAS から組み立てる。印の出どころと確かめ。地図のずれの説明（`DRIFT`）。
- `js/table.js`：表（名前の列と表本体の 2 つの SVG）。`js/list.js`：スマホの手順カード。`js/detail.js`：詳しい欄とコード。
- `js/packet.js`・`js/stagekit.js`・`js/scene-ui.js`・`js/scene-cpu.js`：パケット（再生と絵コンテ）。`js/trace.js`：記録の帯。
- `css/style.css`：明暗両方の色。`shots/`：スクリーンショット。
