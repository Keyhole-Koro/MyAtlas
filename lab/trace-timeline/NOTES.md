# 記録を時間で見る（trace-timeline）

## 考え

記録「Editor で「x」を打った 1 回」を、Perfetto や Chrome tracing のように時間で描く。

- 横は命令の数（時間の代わり）、縦はスレッドごとの段で、下ほど深い呼び出し（フレームグラフ）。
- 色は地図の層。地図のノードの呼び出しは濃く、地図にない関数は淡く描く。
- スレッドが CPU を離れて待っている間は斜線。どの呼び出しで止まって待ったかが見える。
- 列を通ってスレッドをまたいだ要求・返事・イベントは青い矢印で結ぶ（要求 2・返事 2・イベント 2）。
- 上の「あらすじ」は、CPU を持ったスレッドが替わるたびに場面を区切り、地図の言葉で名前を付けたもの。
  1 キー入力 → キーの割り込み、2 キーを配る → イベントを 2 件入れる、3 Editor.edited → 要求を列に並べる、
  4 DOM を書き換える（Window_title）、5 Editor.moved → 要求を列に並べる、6 DOM を書き換える（Label_text）、その後。
  名前は記録の中身（どのノードが、どのスレッドで走ったか）から規則で作っていて、手で書いた文ではない。
- 段の中には、場面の要所に番号の札を立てる（①キーの割り込み ②キーを配る ③Editor.edited ④DOM を書き換える Window_title
  ⑤Editor.moved ⑥DOM を書き換える Label_text）。番号は上の場面と同じで、全体を見た時でも物語の筋が段の中で読める。
- 最初は「要所だけ」で描く。割り込みと syscall は 1 本にたたみ（中の呼び出しはその本の中）、その外も地図のノード・
  アプリの関数・要所だけを残す。editor の段は 13 段から 4 段に、compositor.run は 7 段から 3 段になる。
  「すべて」で記録した呼び出しを入れ子のまま全部描く。
- 「キー → DOM の道筋」は、キーの割り込みから DOM の書き換えまでを、記録の事実と順番だけで 1 本につなぐ。
  Window_title の書き換えまで 409,826 命令のうち 347,346 命令（85%）、Label_text まで 524,990 命令のうち
  445,516 命令（85%）は、イベントと要求が列で待っていた時間だった。

## データについて（大事）

- `ATLAS.traces[0]` には enter・irq・switch・request しか無い（MyAtlas の `traces.py` が exit と iret を落とす）。
  これでは呼び出しの長さも入れ子も分からない。
- そこで同じ記録の元ファイル `MyComputer/docs/atlas/traces/ui-request.json` から、`tools/build-trace.mjs` で
  `data/trace-full.js` を作った（528 イベント全部。exit・iret・from・interrupted・syscall・trap を含み、clock は除く）。
  元ファイルは読んだだけで、変えていない。
- ページは seq ごとに `ATLAS.traces[0]` と突き合わせる（279 件すべて一致）。ノードの対応（`n`）は ATLAS から取る。
- **OS_CALL の対応を 1 か所直している。** `ATLAS.traces[0]` は syscall.dispatch の入口すべてに `n: kernel.os-call` を
  付けている。しかし 12 回のうち 3 回は WAIT_NOTIFICATION の syscall（外側の irq の `syscall` で分かる）。
  `syscall.unsafe.mln` の dispatch は `Syscall::OS_CALL`（484 行）と `Syscall::WAIT_NOTIFICATION`（505 行）を別の枝で
  扱う。この 3 回はノードから外し「syscall.dispatch（WAIT_NOTIFICATION）」と書く。OS_CALL のノードは 9 回・58,270 命令
  （直す前の表示は 12 回・887,983 命令で、9 割以上が WAIT_NOTIFICATION の待ちだった）。カードにも理由と枝のコードを出す。
- 地図にない関数の層は、ファイルの置き場所から推定する（MyOS/src/apps → アプリ、MyAppFramework・MyStdLib → ライブラリ、
  MyOS → OS サービス、MyKernel → カーネル）。地図の関数ノード 36 個すべてがこの規則に合う。推定したものは淡く描き、そう書く。
- 記録にファイルが無い 2 関数（`os_call` と `sys_wait_notification`）は、MyComputer のソースでは
  `toolchain/MyStdLib/platform/myos/syscall.masm` が export している（transport.unsafe.mln もそこから import する）。
  その置き場所から層はライブラリとした。これで「層が分からない」呼び出しは無くなった（アセンブリなのでコードの写しは無い）。
- 割り込みと syscall は irq から iret までを 1 つの枠として描く（OS_CALL は ctx.syscall、割り込みは ctx.irq に結ぶ）。
- 記録の終わりまで戻らなかった呼び出し（開いたまま）が 16 ある。editor の 7 つ（WAIT_NOTIFICATION で通知を待っている）と
  automation_ui.run の 5 つは本当に待っている途中なので、記録の終わりまで描く。走るもの無し（idle）の 4 つは、キーの割り込みが
  compositor に切り替えたあと CPU がその文脈に戻らないだけで、待っているのではない。CPU が離れた 3,509 命令目で切り、
  点線で消えていく尾を付ける。長さは分からないので、表・カード・合計には長さを入れない。

## 使い方

`lab/serve.sh` で開き、`http://127.0.0.1:8765/trace-timeline/`。

- あらすじの場面を押す、← →、1〜7 で場面へ寄る。「順に見る」で 1 から順に流れる。
- 「キー → DOM の道筋」で道筋を見る（まず Window_title、パネルの「次の書き換え」で Label_text）。右に、手順ごとの時刻と、
  列で待った長さが出る。
- 段の中の番号の札を押すと、その要所の呼び出しに寄って説明が出る。
- 「呼び出し：要所だけ／すべて」で、たたむかどうかを切り替える。たたんだ本の上にマウスを置くと「中の 11 回の呼び出しは
  たたんでいる」のように出る。たたんだ中の呼び出し・手順・ノードを選ぶと「すべて」に自動で切り替わり、選択を消す（Esc、
  場面や道筋を選ぶ）とたたみ直す。自分で「すべて」を選んだ時はそのまま。
- タイムライン：ホイールで拡大、ドラッグで移動、目盛りをドラッグで範囲を選ぶ、ダブルクリックでその呼び出しに寄る、
  左の名前を押すと段をたたむ。W S で拡大、A D で移動、0 で全体、Esc で選択を外す。
- 呼び出しを押すと、右の「ノード」にノードの説明・型・呼ばれた道・この中で呼んだもの・この記録での回数とコードが出る。
- 「流れ」タブ：UI の要求・CPU 時間・中の紙（request_gateway.request、request_channel.submit、charge_elapsed、Tasks.tick）の
  手順を押すと、その手順にあたる呼び出しと矢印だけが濃くなり、全体図にも印が付く。
- 「一覧」タブ：全部の呼び出しの表（長さ・始まり・自分だけで並べ替え、スレッドと層で絞る）。図の代わりの表でもある。
  開いたままの呼び出しは長さの代わりに「開いたまま」と書き、長さで並べると最後に来る。
- 時間の軸：「記録外を詰める」（記録した関数が 1 つも開いていない長い間を短く描く）と「実際の長さ」を切り替えられる。
  詰めた間は目盛りの上で薄い帯と // 印になり、幅があれば「14万」のような長さを点線の札で書く。帯のあとの
  「391,616〜」は、そこから時間が再開するという印（ふつうの目盛りとは書き方を変えている）。
- スマホ・タブレット幅（右の欄が下に回る時）：呼び出しや場面を押すと、画面の下に短い説明が出る。「説明 ↓」で下の欄へ。
  タイムラインの上で縦になぞるとページが動き、横になぞると時間が動く。
- アドレスに状態が残る：`#phase=3`、`#path=2`、`#step=ui:4&tab=flow`、`#call=83&tab=node`、`#node=kernel.os-call`、
  `#axis=real`、`#calls=all`。

## うまくいったこと

- 終わりの記録があるので、本当の長さと入れ子が描ける。OS_CALL の中でアプリのスレッドが OS とカーネルを走る様子
  （editor の記録した時間の 88% は OS サービスとカーネル）が、「すべて」で 1 つの段の中に見える。
- 「要所だけ」と番号の札で、最初の画面がそのまま物語として読める：①キーの割り込み → ②キーを配る → ③Editor.edited →
  ④DOM を書き換える → ⑤Editor.moved → ⑥DOM を書き換える が、どのスレッドのどこで起きたか、全体を見たままで分かる。
  幅が 1px に満たない呼び出し（Editor.moved は 37 命令）も、札と最低 3px の幅で見失わない。
- 斜線の「待ち」で、editor が WAIT_NOTIFICATION で止まっている間に compositor.run が serve → handle → set_text を走らせる、
  という受け渡しがひと目で分かる。
- 列を通るメッセージを順番で結んだ矢印で、スレッドをまたぐ因果がたどれる。たたんでいる時は、矢印は描いている呼び出し
  （OS_CALL REQUEST の本や serve）から出入りし、時刻は本当の送った・受け取った時のまま。矢印の札（要求・返事・イベント）は
  番号の札・名前の行・呼び出しの名前を避けて置く。
- 「記録外を詰める」軸で、全体の 82% を占める記録外の時間に押しつぶされず、6 場面が 1 画面に入る。短い場面 1 も見える。
- 流れの手順との照合を絞った：呼び出しの入れ子、紙の中の順番、OS_CALL(X) の service、紙の中だけ、列を通るメッセージ。
  例えば「OS_CALL(REQUEST)」は 12 回の syscall のうち REQUEST の 2 回だけが濃くなる。
  記録に出ない端は理由を書き分ける：記録していない関数（44 の外）なので分からない／記録している関数だが呼ばれていない／
  関数の中の 1 文・1 つの枝／置き場・データの形・エミュレータの部品。CPU 時間の「先に足す」は fill() を記録していないので
  起きたか分からないと書き、charge_elapsed を代わりに誰が呼んだか（reschedule ×13 など）を示す。
- 表示中の範囲の層の割合が、拡大や移動に合わせて変わる。左の名前の下にはスレッドごとの層の割合。
- 暗い色の画面、スマホ幅（名前を段の上に置き、矢印と札はその行を避ける）でも読める。待ちの本の上の名前は、
  1 色の文字を淡い下地に載せ、濃い部分と淡い部分の境で色が変わらない。

## うまくいかないこと・限界

- 記録しているのは 44 関数だけ。82% の時間は記録外で、その間に何が走ったかは分からない。「自分だけ」の時間は、
  記録した呼び先と待ちを除いた長さで、記録していない呼び先の分は含む（画面にもそう書いている）。
- メッセージの対応は順番による（列は先に入れたものから出る）。channel の番号は記録に無い。
- イベントの種類は記録に残らない。UI の流れの「TIMER」の手順は「同じ道 2・種類は不明」とだけ言い、
  この記録のイベントが dom_widgets.dispatch_key_event の中で入れられたことを添える。
- 道筋の 2 つのつなぎ（キーの割り込みから compositor への切り替え、ハンドラから属性のフック）は、記録の順番と
  地図の説明（kernel.irq-dispatch と lib.send-text）による。画面にもそう書いている。
- 「記録外を詰める」は、記録外を詰めるだけでなく、全体の 5% に満たない場面（場面 1、3,509 命令）を 5% まで広げる。
  その場面の中だけ目盛りの間隔が違う（ボタンの説明に書いている）。正確な比べ方は「実際の長さ」で。
- 「要所だけ」は割り込みと syscall の中を見せない。OS_CALL の本の中の gateway・submit などは「すべて」で見る（手順や
  ノードを選べば自動で切り替わる）。たたんだ本の色は割り込み・syscall の枠の色（カーネル）で、中で走った OS サービスの
  色ではない。
- 番号の札と場面の名前の規則は、この地図のノード（os.submit、os.ui-protocol、os.events など）と道筋に結びついている。
  別の記録では言葉や札が足りないことがある。
- UI の要求の流れはタスクマネージャの例で、記録はエディタ。view() と tick() は記録していない関数なので分からない（そう表示）。
- canvas なので、呼び出しをキーボードで 1 つずつ選べない（一覧の表が代わり）。スマホでは「すべて」の深い段は細かい。
- `os_call`・`sys_wait_notification` の置き場は記録ではなく MyComputer のソースから補った（コードに書いている）。

## 本体の viewer に取り入れられること

1. `traces.py` で exit と iret（と from・interrupted・syscall・trap）を残す。それだけで長さ・入れ子・待ちが描ける。
2. `traces.py` で `kernel.os-call` を付けるのは、外側の irq の syscall が OS_CALL の syscall.dispatch だけにする
   （今は WAIT_NOTIFICATION の 3 回も OS_CALL になっている）。記録にファイルが無い `os_call`・`sys_wait_notification` には
   MyStdLib の syscall.masm を入れる。
3. スレッドごとのフレームグラフと、斜線の「待ち」。
4. 「要所だけ」のたたみ方（割り込み・syscall を 1 本に、外は地図のノード・アプリの関数・要所だけ）と、たたんだ中を選んだら
   自動で開いて、選択を消したら戻すやり方。
5. 場面の番号を付けた札を、要所の呼び出しの真上に立てる（あらすじと段をつなぐ）。
6. 「記録外を詰める」時間の軸（詰めた間は帯と 1 つの // 印、長さは帯の中の札かツールチップ、再開は「391,616〜」）。
7. CPU の番で区切ったあらすじと、その名前を地図の言葉（ノードの説明、手順の動詞）から付けるやり方。
8. 手順と記録の照合の絞り方（入れ子・紙の中の順番・OS_CALL の service・列を通るメッセージ）と、記録に出ない理由の書き分け
   （記録していない／呼ばれていない／1 文・1 つの枝／置き場）。
9. キーから DOM までの道筋と、列で待った割合。
10. 表示中の範囲の層の割合と、スレッドごとの層の割合。

## レビュー後に変えたこと

- 【高】WAIT_NOTIFICATION の syscall.dispatch 3 回が OS_CALL と書かれ、OS_CALL のカードが 12 回・887,983 命令と言っていた
  → 外側の irq の syscall で見分けてノードから外した。OS_CALL は 9 回・58,270 命令。カードに「12 回のうち 3 回は
  WAIT_NOTIFICATION なので数えない」、外した呼び出しのカードに理由と WAIT_NOTIFICATION の枝のコード（505–514 行）を出す。
- 【中】詰めた軸の目盛りが読みにくい → 記録外の長さを目盛りと同じ行に数字だけで書くのをやめた。詰めた間は薄い帯と 1 つの
  // 印（前は 2 つ）、長さは帯に入る時だけ点線の札（「14万」）、ほかはツールチップ。再開の印は「391,616〜」と太字で書き、
  ふつうの目盛りと分けた。場面 1 は全体の 5% まで広げ、どの場面も番号が見える。凡例に「記録外（詰めた間）」を足した。
- 【中】最初の画面がカーネルと OS の枠の壁で、アプリの関数と DOM の書き換えに名前が無い → 「要所だけ／すべて」を足して
  「要所だけ」を最初の表示にした。番号の札（①〜⑥）を要所の真上に立て、要所とアプリの関数は最低 3px で枠を付けた。
  時間の軸の中のあらすじは、番号と、全体が入る時だけ題（1 語で切れた「イベント…」は出さない）。
- 【中】スマホで矢印の札が名前の行に乗る・縦になぞってもページが動かない・押した説明が遠い → 名前の行には矢印も切り替えの
  線も札も描かない。`touch-action: pan-y` にして縦はページ、横は時間。押すと画面の下に短い説明と「説明 ↓」を出す。
  ブラウザがなぞりを引き取った時（pointercancel）は押したことにしない。
- 【中】閉じない枠が本当の長さのように見えた → 表は「開いたまま」と書いて長さの並べ替えで最後に。走るもの無しの 4 つは
  CPU が離れた所で切って消えていく尾を付けた。ノードのカードの合計から外し、そう書く。「この中で呼んだもの」も同じ。
- 【中】記録していない関数を「この記録には出てこない」と書いていた → RAW.watched を先に見て書き分ける
  （記録していない関数なので分からない／記録している関数だが呼ばれていない／関数の中の 1 つの枝）。手順の札も
  「記録外の関数」と「記録になし」に分けた。
- 【低】「全体」や 0 のあと範囲の文字が途中の値のままだった → 誤差を許して「記録全体」と判定し、キャッシュの鍵にも入れた。
- 【低】「自分だけ（呼んだ先と待ちを除く）」が言い過ぎだった → 「記録した呼び先と待ちを除く（記録外の呼び先は含む）」。
- 【低】凡例に灰色が無い・スマホで区切り線が行末に残る → 灰色の呼び出しは置き場所を補って無くなった（残る時は凡例に出す）。
  区切り線をやめて、凡例を 2 つのまとまりに分けた。
- 【低】濃い部分と淡い部分の境で名前の色が途中で変わる → 待ちの本の名前は 1 色にして淡い下地に載せた。
- 【低】日本語が語の途中で折れる・道筋のボタンが 2 つ目から開く → 場面の題は句ごとのかたまりで折り（`word-break: auto-phrase`
  も使う）、道筋は Window_title から開いて「次の書き換え（Label_text）→」を出す。
- ほか：短い syscall の本には「POLL」「REPLY」のような短い名前を出す。矢印の札は、ある程度短い矢印にも付ける（前は要求の
  矢印に札が無かった）。

## ファイル

- `index.html`、`style.css`：ページ。
- `js/model.js`：記録から、呼び出し・スレッド・メッセージ・場面・道筋・要所・たたみ方・手順との照合を作る。
- `js/main.js`：描画と操作（canvas、ライブラリは使っていない）。
- `data/trace-full.js`：`node lab/trace-timeline/tools/build-trace.mjs` で作る（元は MyComputer の記録）。
- `shots/`：main（最初の画面：要所だけ・番号の札）、path（Window_title までの道筋）、phase3（場面 3・たたんだ
  OS_CALL REQUEST のツールチップ）、flow（UI の手順 OS_CALL(REQUEST)：「すべて」に切り替わり REQUEST の 2 回だけ濃い）、
  dark（暗い色・WAIT_NOTIFICATION の dispatch のカード）、phone（スマホ幅・押した呼び出しの短い説明）。
